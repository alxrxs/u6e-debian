# Debian on the Ubiquiti UniFi U6 Enterprise

This repository turns a UniFi U6 Enterprise Wi-Fi access point into a small Debian 13 (trixie) computer running Linux 7.2.8, with all three radios working as a full-featured Wi-Fi 6/6E access point.

The U6 Enterprise has a Qualcomm IPQ5018 chip (two ARM cores, an internal 2.4 GHz radio), two QCN9074 radios for 5 GHz and 6 GHz, and one 2.5 GbE network port. Debian runs entirely from RAM, started next to the untouched stock firmware, so the stock system is always one reboot away. Qualcomm's NSS (a separate network processor inside the chip) does the packet forwarding in hardware, including for Wi-Fi.

The only thing ever written to the SPI flash (the small chip holding the boot loader) is the boot loader's settings, which hold the command that starts Debian (see [Booting](#booting)).

## What you need

- An x86 Linux build machine with the aarch64 cross compiler (and the armhf one, for the 32-bit boot shim), `mmdebstrap`, `qemu-user-static`, `u-boot-tools`, rustup, and exactly this cross toolchain (the agent and the controller are built through zig's C toolchain, and another version of any of it builds another binary):
  - Rust 1.97.1 with the `aarch64-unknown-linux-musl` and `x86_64-unknown-linux-musl` targets, pinned by `rust-toolchain.toml` (rustup installs it on the first `cargo` run in the checkout);
  - `zig` 0.17.0 (the official release tarball) and `cargo-zigbuild` 0.24.0 (`cargo install --locked cargo-zigbuild --version 0.24.0`), pinned by `toolchain.env`.

  `deploy.sh` checks all three versions before it builds the agent and stops on any other.
- Optionally, an Apple silicon Mac with OrbStack, reachable over SSH (`NATIVE_BUILD` in `site.conf`): the arm64 package and root filesystem builds then run there natively, many times faster than under `qemu-user-static`.
- SSH access to the stock firmware of each access point (the stock login set in `site.conf`).
- `site.conf`: your site's settings. Copy `site.conf.example` and fill it in; it is never committed. It holds:
  - the management network (VLAN, gateway, DNS, NTP, syslog collector) and the VLANs Wi-Fi clients land in;
  - the Wi-Fi plan: country, one line per SSID (name, kind, bands, default VLAN), channels, transmit power, and the optional 6 GHz Multiple BSSID setting;
  - how secrets are fetched: passphrases, the roaming key, the RADIUS-over-TLS certificate and the stock login are read by small shell functions, so they can come from a file or a password manager;
  - optionally, the controller `u6e-agent` streams to: its address and its public key (plain values), with each access point's own private key read by a shell function in that access point's block; and the public half of the controller's configuration key (`CONFIG_KEY`), whose live Wi-Fi configurations alone the images apply;
  - one block per access point (hostname, address, LED colour, Wi-Fi colours, and optionally its SSH host key, read by a shell function), and the test client for `test/`;
  - optionally, `AP_KNOWN_HOSTS`: the known_hosts file the boot tooling checks the access points' host keys against (see [Booting](#booting));
  - `U6E_PERSIST` (see [Booting](#booting)) and `BLOBS`, the location of the proprietary files below;
  - optionally, the experimental `NSS_SHAPERS` and `U6E_PCC`, off unless set (see [What the access point does](#what-the-access-point-does)).
- `$BLOBS`: a separate private repository with the proprietary files the build reads from it. They are not redistributable, so they are not included here:

| Path under `$BLOBS/` | What it is |
|---|---|
| `wifi/firmware/ipq5018-WLAN.HK.2.7.0.1-01744/` | Wi-Fi firmware for the internal 2.4 GHz radio |
| `wifi/firmware/qcn9074-WLAN.HK.2.13-01309/` | Wi-Fi firmware for the 5 GHz and 6 GHz radios |
| `wifi/board/linux-firmware/{IPQ5018,QCN9074}/` | Board data (calibration tables) from linux-firmware |
| `wifi/board/stock-a654/` | Board data for this model, taken from the stock firmware |
| `bt/firmware/` | Bluetooth firmware, taken from the stock firmware |

The NSS firmware is downloaded by the build and checked against a pinned checksum.

## Quick start

```sh
cp site.conf.example site.conf    # then edit it
sudo ./deploy.sh                  # build everything and boot every access point in U6E_APS
sudo ./deploy.sh ap1 ap2          # or only the named ones
sudo BOOT=0 ./deploy.sh           # build everything, each image included, but boot nothing yet
sudo FORCE=1 ./deploy.sh ap1      # boot ap1 again even though it already runs the current build
```

`deploy.sh` runs these steps in order and skips any whose inputs have not changed since the last run (it records them in `stamps/`; logs go to `log/`):

1. `trees.sh`: prepares the kernel and Wi-Fi driver sources (see [Sources and patches](#sources-and-patches)).
2. `fw/mk-board2.sh`: assembles the board data files for the radios.
3. `config-u6e.sh` and `make`: configures and builds the kernel.
4. `nss/build.sh`: builds the NSS drivers, our `u6e-pcc` module and the Wi-Fi stack, and fetches the NSS firmware.
5. `pkg/hostapd/build.sh`: builds hostapd (the program that runs the Wi-Fi networks) as a Debian package.
6. `pkg/iproute2-nss/build.sh`: builds Debian's `iproute2` with the NSS traffic-shaping options added to `tc`.
7. `pkg/netlogd/build.sh`: builds Debian's `systemd-netlogd`, which forwards the log, with a fix for its journal file rotation.
8. `mkrootfs.sh`: creates the Debian root filesystem.
9. `pkg/u6e-agent` (a member of the cargo workspace in `Cargo.toml`): builds the access point's resident agent (Rust, one static binary): the neighbor report exchange between access points, the management network check, the state line in the log, the collectors that read the access point's Wi-Fi state (nl80211, hostapd, sysfs, the kernel log) into snapshots and events and its clients' connections (ECM's connection table, through `/dev/ecm_state`) into per-client flows, and, when given a controller (`--controller`, `--key`, `--controller-key`), the link that streams them to it over post-quantum TLS with pinned keys and carries out its commands. It runs as its own user `u6e-agent`, with no capabilities and in a tight systemd sandbox: hostapd gives that user's group its control sockets, `u6e-nss` creates ECM's state device for that group (each open of it is a new dump, so the agent opens it itself, allowed by the unit's `DeviceAllow`), systemd opens the root-only files it reads (the NSS load in debugfs, its private key), and it asks for `u6e-arm`/`u6e-fallback` through files their path units watch, as it may start no unit itself.
10. For each access point whose running image was built from other inputs (the parts of this repository that go into an image, which `ap-image.sh` lists, with only the agent's dependencies of `Cargo.lock`; `$BLOBS`, `site.conf` or the source trees): `prep-rootfs.sh` builds its image, unless the image built last for that access point (recorded in `stamps/built-<ap>`) has these inputs and is still in `images/` (`ap-image.sh` makes this choice); `boot/stage.sh` boots that image, and `deploy.sh` waits until all three radios are up. An access point already running the current build is left alone; `FORCE=1` boots it anyway, with the image already built for the current inputs if there is one (delete `stamps/built-<ap>` to build a fresh one). With `BOOT=0` each image is built and kept but not booted, so the access points keep running until a later run boots that same image. Before the first access point, `deploy.sh` takes a lock on `images/`, which `prune.sh` takes too, and refuses to go on while another holds it, so two deploys of a tree never have two access points down at once. A site whose controller rolls images out (`pkg/u6e-controller`) builds with `BOOT=0` and hands the controller each image to keep (`u6e-controller image add`), which then stages it itself: `deploy.sh` and the controller do not know of each other's stagings, so a site boots its access points through one of them.

Every image is kept in `images/` with a `MANIFEST` (versions and checksums), so an earlier build can be booted again without rebuilding. The image itself carries its `images/` name, its build time (`built_ms:`, milliseconds since the epoch) and the same versions in `/etc/u6e-image`. After a run that went through for every access point, `deploy.sh` prunes the kept images (`prune-images.py`; `prune_images <tree>` prunes another tree by this checkout's rule and script): it keeps each access point's running image (`stamps/running-<ap>`), its image of the current inputs (`stamps/built-<ap>`) and the newest `KEEP_IMAGES` (3) of each access point, and prunes nothing while what an access point runs is not known. A stamp is read only if it is a small regular file (no link followed, no FIFO waited on). An image is first renamed to `.<id>.pruning`, then emptied, so a prune cut short leaves nothing under an image's name (the next prune removes it), and nothing takes a dot-name for an image. A run starts only with `MIN_FREE_GIB` (15) GiB free, in bytes, on the tree's filesystem. To free room by the same rule outside a run, as root: `./prune.sh --dry-run` lists what it would remove, `./prune.sh` removes it, under the kept images' lock.

## Sources and patches

The kernel and the Wi-Fi drivers are stored here as a download address plus a series of patches, not as copies of the upstream code:

- `kernel/`: Linux 7.2.8 (`kernel/source`) and 126 patches (`kernel/patches`) for this board and for NSS.
- `backports/`: OpenWrt's backports of the Linux 7.2 wireless stack (`backports/source`) and 196 patches (`backports/patches`) adding NSS Wi-Fi offload and fixes.

`./trees.sh` downloads each release (checked against its checksum), applies the patches as git commits and produces the working trees `linux-7.2.8/` and `backports-7.2/`. The commit IDs come out the same every time. To change something, commit in a tree and run `./export.sh kernel` (or `backports`) to turn your new commits back into patch files. `trees.sh` refuses to overwrite a tree whose work has not been exported.

Patches keep their original authors. We are sending our patches to the upstream projects (the kernel and hostapd).

## Booting

Ubiquiti's boot loader (U-Boot) is 32-bit and only starts its own signed images, but it will start any 32-bit ARM kernel. `shim/` is a tiny 32-bit program (208 bytes) that asks the chip's TrustZone (its built-in secure firmware) to restart the processor in 64-bit mode at our kernel.

`boot/go8.sh` does the staging while the stock firmware is running. It copies the shim, the kernel, the device tree and the initial filesystem into stock's data partition on the eMMC (changing only the parts that differ), and writes a one-shot U-Boot boot command that loads them. The next reboot starts Debian. The reboot after that returns to stock, because the command removes itself as it runs. `boot/stage.sh` does the whole cycle for one access point, from either system, and `boot/apstate.sh` tells you which system is running.

Both systems answer SSH on the access point's address, each with its own host keys. An image never carries the root filesystem's keys, which every image built from it would share: with `ssh_host_key` in its block in `site.conf`, an access point's image carries that Ed25519 key, the same in every image of it; without it, the image makes new keys at every boot, as it lives in RAM. With `AP_KNOWN_HOSTS` set, the boot tooling checks every host key against that file, our image's under the alias `<AP_HOSTNAME>` and stock's under `<AP_HOSTNAME>-stock`, and refuses a key it does not hold; without it, it checks none.

Persistent mode: with `U6E_PERSIST=1` in `site.conf`, the image re-arms the boot command once the management network is reachable (`u6e-agent` checks it every minute and asks for `u6e-arm`), so reboots and power cuts come back into Debian. If the network never comes up, or is lost later, `u6e-fallback` removes the boot command and the access point returns to stock instead of looping. `u6e-arm disarm` does the same by hand. Each Debian boot in persistent mode writes the 64 KiB U-Boot settings area twice.

## What the access point does

Wi-Fi starts by itself on every boot (`u6e-wifi.service`), with nothing else on the network needed. The access point has no battery-backed clock, so Wi-Fi first waits up to 60 seconds for NTP: hostapd checks the RADIUS server's certificate against the time. `boot/wifi-up.sh` generates the configuration from `site.conf`, and can install a changed one on a running access point (with a restart of `u6e-wifi`, which drops any configuration applied live since boot).

**Networks**
- Three kinds of SSID, each on the bands you choose: WPA3-Personal, WPA3-Enterprise, and WPA2-Personal with MAC-address authentication for old devices that can do nothing newer.
- Enterprise logins are checked by your RADIUS server over TLS ("RadSec") spoken directly by hostapd. RADIUS can also place each client in its own VLAN.
- Optional 6 GHz Multiple BSSID: all 6 GHz networks share one beacon.

**Roaming and client help**
- Fast roaming between radios and access points (802.11r). The access point a client leaves drops it as soon as the other one's Layer 2 Update frame for it arrives over the wire, unless the client still transmits to it within two seconds (our hostapd patch `pkg/hostapd/roam-prune.patch`, `prune_roamed_sta`). Otherwise a client that still acknowledges some frames on the old channel, as Apple devices visiting it for AWDL do, stays associated there, and the NSS keeps sending that access point's traffic for it into the air (a HomePod stereo pair's second speaker is silent while its partner's audio for it goes there).
- Roaming advice for clients (802.11k and 802.11v). The access points send each other lists of their networks every 10 seconds (`u6e-agent`, a single small process that changes hostapd's lists only when they differ), so clients are told about the others.
- Optimized Connectivity (OCE), Agile Multiband (MBO) and Wi-Fi QoS Management, which help clients pick the best band and mark their traffic correctly.
- Beacon protection on 5 GHz and 6 GHz, which stops forged beacons.
- Time-of-flight ranging for indoor location, 6 GHz discovery frames, and 6 GHz announcements on the 2.4 and 5 GHz beacons so clients find 6 GHz quickly.

**Speed**
- Packet forwarding, Wi-Fi offload and encryption run on the NSS processor.
- Multicast and broadcast (mDNS, SSDP, ARP, IPv6 neighbor discovery) reach every client, each as unicast at its own rate, and a client's broadcasts reach the other clients on its network; nothing is isolated, proxied or snooped, so AirPlay and HomeKit devices find each other.
- The usual Wi-Fi 4/5/6 speed features are enabled: beamforming, TWT and spatial reuse among them.

**Running it day to day**
- The whole system log goes to your syslog collector (the access point keeps logs only in RAM), the kernel log goes out over the network, and `u6e-agent` adds load, memory, clients per network, temperatures (the SoC's sensors and each radio's own) and Wi-Fi firmware crashes every 5 minutes.
- With `CONTROLLER` set in `site.conf`, `u6e-agent` also streams the access point's Wi-Fi state (radios, networks, clients, events) and its identity (`/etc/u6e-image`) to the controller over post-quantum TLS, each side pinning the other's key. Each client goes with how it authenticated, as hostapd holds it for its association (`STA`, asked once per association, again each tick until hostapd authorizes it, at most 16 a tick, the stations taking turns, and nothing more that tick of a hostapd that did not answer in time; an answer about another station is not taken): its AKM suite, whether the association was a fast transition (802.11r), whether hostapd authorized it, and over 802.1X the identity it gave EAP, its EAP method and the reauthentication period RADIUS set; its VLAN is the one RADIUS put it in. The same answer says what the client supports, as it announced it when it associated, on the band of its network: its newest PHY mode (HE, VHT, HT or legacy) by its flags, and from that mode's capabilities its spatial streams and highest MCS (the receive map, what the access point may send it) and its widest channel (an HE client's for the band, VHT's 160 MHz bit, HT's 40 MHz bit); which capability lines count goes by the flags hostapd prints before the identity, so an identity holding newlines cannot claim a mode its client did not. The events include EAP starting, succeeding, failing and timing out (the client gone silent, or the RADIUS server), a passphrase that does not match, a client asking for BSS transition candidates (an 802.11v query, with its reason) and a client's answer to a BSS transition request, whoever sent it (its status code and, accepting, the network it said it moves to): hostapd sends all of them to the agent's event sockets anyway. A client's rate each way is that of its last frame, as nl80211 reports it, except that an HT/VHT/HE client's last such rate stands for up to a minute over the legacy rates of the management and control frames between its data frames. A radio stays in the stream once seen, reported down while it serves no network (its hostapd exited, say), so its outage shows as a radio down rather than as no radio. Each client's connections go too: their count, how many the NSS hardware forwards (one that has ended counts by where most of its packets went, since ECM keeps it, decelerated, for minutes after it closes), their bytes and packets each way and the 6 largest, every minute, every 10 s while the controller asks for it (or a second per 30 connections in the table when that is longer, 33 s at 1000, up to the minute, so the reads stay near 0.2 % of a core), and every connection (up to 4096) on request. They come from ECM's connection table, so no packet is looked at on the access point's CPU; a connection between two of its clients counts for both. ECM writes each connection in brief for it (our patch `nss/patches/qca-nss-ecm/902`, 14 lines where the full record has 175, whose writing costs the access point about 0.4 ms of CPU per connection), and `u6e-agent --print-flows` prints the flows and what a read cost. The controller can also kick a client, block or unblock it on every network of the access point, and steer it to another network of its SSID (802.11v, a request the client may decline, staying where it is; the result says whether it accepted, declined and why, or did not answer within 3 s), or force the move, when a client that declines is disassociated about 10 s later; the access point keeps blocks in RAM only, and on every connection the controller sends its whole list, which every network's deny list is then made to hold exactly, so a client unblocked while the access point could not be told is let on there too. The access point works the same without it.
- Each radio is named after its band, `radio24`, `radio5` and `radio6` (its wiphy, as `iw` and the agent show it), and its interface `wlan24`, `wlan5` or `wlan6`, by the device it sits on: the kernel numbers the radios in the order they probe, which can swap the two QCN9074s from one boot to the next, so a name derived from that number would carry another radio's history after a reboot.
- Each radio reports its temperature (`/sys/class/ieee80211/radio*/hwmon*/temp1_input`), and its firmware throttles transmission when it runs hot, in steps with hysteresis: the 5 and 6 GHz radios stop transmitting half of the time above 100 °C, 90 % above 105 °C and entirely above 110 °C (back down below 95, 100 and 105 °C); the 2.4 GHz radio does the same above 105, 110 and 115 °C.
- With `CONFIG_KEY` set in `site.conf`, the controller can apply a new Wi-Fi configuration without a reboot: each radio's hostapd file as `boot/wifi-up.sh` makes it and its transmit power, known by its SHA-256, which the access point reports of what it has installed. The controller signs each configuration with its configuration key, a key of its own apart from its link's (Ed25519, over the protocol, the access point's name, a sequence number that grows with each one, the end of its ten minutes of validity, and the hash), so no one who can only speak on the link can make an access point run a configuration, or an older one again. This is the only way the radios' configuration changes, so the reported hash always says what runs. `u6e-agent` checks the signature, the sequence, the hash and every file (no file named outside hostapd's own run directories, the radios those of the access point, a new channel or power one the radio and the regulatory domain allow now). Each radio then takes it the least disruptive way: settings hostapd reads at each use (the BSS load period, DTIM, FILS Discovery, RNR, inactivity limits) are set in place on the running hostapd; a new channel or width goes by a channel switch announcement over 5 beacons, unless it is a DFS channel that needs a radar check (CAC) first, which no switch runs: u6e-wifi then restarts onto it, its hostapd checking off the air (a minute, ten on the weather radar channels, which the helper waits for); a new power alone is set through nl80211; anything else restarts `u6e-wifi` after every client is asked to move to the other access point (802.11v). A step that fails is undone. hostapd's own reloads are not used: they disconnect the clients or give their networks new group keys without telling them. The configuration lives in `/run/u6e-wifi`, root's alone (it holds the passphrases and keys), so a restart of `u6e-wifi` keeps it until the next boot. `u6e-agent --config-helper` is a root helper started by its socket for the agent's group alone. It tells the agent how each radio takes a configuration, since the agent never reads the installed one. The sequence numbers are the controller's signing times in milliseconds, and the image's build time is their floor: a configuration signed before the image was built never applies on it, not even after a reboot has forgotten the last one applied. Nor does one past its validity, by the access point's clock, and none applies until systemd-timesyncd has synchronized that clock (the access point has no RTC, so it boots at its image's build date). The helper checks the signature, the sequence (which outlasts the agent) and every file again, writes each file beside the old and renames it over, publishes the new hash for the agent, and puts the previous configuration back if the radios do not come up after a restart. The configuration passes through the agent in memory only, never shown or logged, and is wiped after use.
- The client guards (`u6e-guard`, a helper of its own user with CAP_NET_RAW and CAP_NET_ADMIN alone, ambient so `tc` has them too, started at boot): ARP inspection, a rogue-DHCP guard, an RA guard, an IP source guard and a ban on VLAN-tagged frames, on every Wi-Fi port (a BSS or a per-VLAN interface of RADIUS-assigned clients, each a port of its VLAN's bridge `br<vid>`). A packet socket on every interface, receiving only and behind a classic BPF program, reads the frames that bear on them as they reach the host: ARP, DHCP and router advertisements always do (they never ride the NSS fast path, and DHCP's unicast renewals were seen to as well), a client's connection only until ECM offloads it, which is its first packets (a TCP SYN, a UDP datagram), and tagged frames whether the tag is in the data or the kernel took it off (the socket's auxiliary data). Unicast between two clients of one BSS is forwarded inside the NSS and never reaches the host, so ARP inspection sees a client's broadcast ARP and its ARP to anything outside its BSS. Each client's MAC is bound to the IPv4 addresses the site's DHCP server acknowledges on the uplink (its server identifier the site's, through the site's relays: other servers' answers bind nothing and are reported; learnt leases are timed on the boot clock, which the first clock synchronization does not move), to those the controller seeds from the DHCP servers' leases (so a client that roamed in is bound too) and to the static ones the controller gives. The guards name only what is provably wrong, so that a client they know nothing of (a static address nobody listed, a lease the seed has not brought) is never in its way, and every frame enforcing drops is one they report, as dropped: they read each frame as the kernel's flow dissector reads it for `tc`'s flower, so what they name is what the filters can match. They name a client's ARP claiming an address bound to another MAC, or, when either MAC holds an address, naming another MAC than the frame's as its sender (an ARP packet flower cannot parse names none); anything from a DHCP or DHCPv6 server port to a client port, malformed or not; a client's router advertisement offering a default route, naming DNS servers or domains, sitting behind an extension header, malformed, or carrying a prefix or a route that is not unique local (a route of /48 or longer: what a Thread border router advertises for its mesh, as HomePods and the like legitimately do); ICMPv6 whose type flower cannot read, which may hide an advertisement (a first fragment of ICMPv6 or of more extension headers, more than the 15 extension headers flower reads through, cut short or of type 0); a connection opened (a TCP SYN, a UDP datagram or any fragment of one) from an address bound to another client, whose other traffic, its DHCP to the servers included, passes; and any tagged frame. A client's own DHCP release or decline unbinds the address it gives up. Each is reported to the agent (at most once a minute per client and guard, with the repeats counted, saying whether it was dropped), which forwards it to the controller. They only report until the controller says to enforce on a VLAN; there `tc` ingress filters on one shared block on that VLAN's Wi-Fi ports (`act_gact`, `cls_flower`, `cls_u32`, `cls_matchall` and `sch_ingress` load at boot) drop exactly those frames, never the client: every tagged frame, everything from a DHCP or DHCPv6 server port to a client port, ICMPv6 whose type flower cannot read, every client advertisement but one with router lifetime 0 and no extension header (u32 reads the field), every advertisement of a client that sent a rogue one in the last hour (each reported as dropped), ARP claiming a bound address from another MAC, and a TCP SYN or UDP from a bound address from another MAC, a binding's filters added and removed with it, each guard's drops counted by an action of its own. Their first and last steps remove their qdiscs and actions and fail loudly when they cannot, so nothing drops while the guards are not running, and an access point that has not heard from the controller since it booted only reports. The same socket takes the mDNS the bridges carry (UDP to or from port 5353 over either IP, whole, from the Wi-Fi ports and the uplink: it is multicast, which the NSS never offloads, so every message reaches the host), which they keep as one bounded table of the devices heard (their port, host name and addresses), the services they offer (from their PTR, SRV and TXT records, each extending the offer's life, of which only the TXT keys `model`, `md`, `gid`, `igl`, `gpn` and `tsid` are kept; a PTR, or an SRV naming the offer's target, of TTL 0 is a goodbye) and the queries they send, and nothing else of a message. A query opens a one-second window per question name in which each live offer it asks for answers, is listed by an asker as a known answer (so its owner rightly keeps quiet, RFC 6762 7.1) or misses; a window counts no miss when every question in it asked for a unicast answer (QU), when a query sent unicast or from another port than 5353 joined it (their answers go back to the asker alone and may never reach the host), or when its lists of names filled up, and a probe opens none. An offer past its TTL is unconfirmed, not gone (a device may stay quiet while nobody asks); it is withdrawn by its goodbye, or by a query it does not answer after the lapse. A query's lists of who answered, missed or was known hold 16 devices each, the rest counted. The parser is bounded against hostile messages: a compression pointer must point strictly back, a name is at most 255 bytes, a message yields at most 64 questions and 128 records and its names take at most 2048 labels and pointers in all, and a name is read as a hash, its text made only for the names the table keeps (at most 160 bytes); the messages are taken 40 a second in bursts of 200, the rest counted, so a crafted flood costs a bounded share of a core (the worst message about 9 µs on the build host against 1.2 µs for real ones). The table is bounded too (96 devices, 256 offers and 256 queries, 32 of each a device, 64 open windows, the least recently heard evicted for a new one; devices, dead offers and queries unheard for an hour forgotten; the whole table at every cap encodes in under half a frame); the agent reads what changed of it each tick, and logs a read that fails.
- The radios' spectral scan (FFT samples of the channel, read through debugfs) runs while the controller asks for it, through `u6e-agent`, and never longer than 10 minutes at a time or past the agent's session with the controller: `u6e-spectral`, a root helper started by its socket and sandboxed to the radios' spectral files, scans a radio's own channel while it serves clients (8 samples of 256 bins every 125 ms), turns them into dBm per bin, holds each bin's peak and hands the agent at most 8 frames a second; the scan stops when the agent asks, disconnects or the helper ends. Measured on a 5 GHz radio at 80 MHz: scanning without pause (ath11k's `background` mode, about 2300 samples a second) changed neither its busy nor its transmit time, but cost the kernel about a third of a core, hence the bounded rate.
- A hang triggers a reset by the watchdog (a hardware timer), and crash information survives the reset so it can be read back from stock.
- When a radio's firmware crashes, the driver restarts it, and the access point keeps the latest firmware crash dump in `/var/lib/u6e-coredump/` (compressed: about 4 MB for a 5 or 6 GHz radio, 12 MB for the 2.4 GHz one, whose dump holds the whole WCSS region and the M3 dump area its firmware fills; readable by root only) and logs its name.
- Each radio's own calibration is loaded at boot, and the status LED can be set to off, blue or white.
- Bluetooth (LE and Classic) works with BlueZ under the stock firmware's address, the board's base MAC + 4: the controller stays unconfigured until `u6e-btaddr` gives it that address at boot. With `BT_POWERED=0` in `site.conf` it stays off until powered by hand (`bluetoothctl power on`). Never unload `btqcomipc` on a running access point: the SoC hangs until the watchdog resets it.
- Rate limits, per client and per SSID, each direction, enforced by the NSS processor's shaper rather than the CPU, as the controller sets them: `u6e-shaper`, a root helper with CAP_NET_ADMIN alone started by its socket for the agent, builds `nsshtb` trees on the BSSs' netdevs (download; a per-VLAN netdev takes no shaper, its BSS's carries its traffic) and on the uplink (upload), a class per limit, and an nftables `netdev` table that tags each limited client's packets with its class, which ECM carries into the offloaded connection (`nss/patches/qca-nss-ecm/903`). A client's own limit replaces its SSID's, direction by direction; an SSID's download limit holds on each of its radios apart. The firmware has one interface shaper unless `NSS_SHAPERS` gives it memory for more, and a limit it cannot take is reported refused with its reason, never shaped by the CPU instead. A sync that built the uplink's tree is undone unless the agent confirms that its link to the controller still flows through the uplink; undoing takes every tree and tag down and builds the shaping before from its spec, so every limit lapses for those moments, not only the ones the sync changed. While the controller is away the limits stay in place and follow clients that roam and BSSs made again; only a limit that needs the uplink's tree built waits for the controller.
- A client's capture, as the controller asks for it: `u6e-capture`, a root helper with CAP_NET_RAW and CAP_NET_ADMIN alone started by its socket, one capture at a time, reads the client's frames on the Wi-Fi ports, each once, behind a classic BPF program built from a closed filter (protocol, port, host), cut at the snaplen asked for, at most 10 minutes and 50 MB, and streams pcapng to the agent, which forwards it to the controller as it acknowledges it. Its traffic the NSS offloads is taken by the NSS mirror where the image loads `u6e-pcc` (`U6E_PCC=1`), else off the offload for the capture, the client's flows and no other client's: a nftables table marks its frames both ways, which ECM keeps on the CPU (our ECM patch 904), and its connections are decelerated. Either way the offload comes back whatever ends the capture: what it changes is written first to a restore file the unit's last step puts back, its runtime is capped, and the agent reports an offload held back. Traffic between two clients of one BSS never reaches the host (the radio forwards it), so no capture holds it. The radios capture nothing on the air: a monitor interface cut an associated client's traffic while it existed.

**Experimental (off unless set in `site.conf`)**

These are under test and change what an image does, so an image built without them does none of this:
- `NSS_SHAPERS=<MB>` gives the NSS firmware that many MB of host RAM for its shapers at boot (`qca-nss-drv qos_mem_size`), kept until the next boot, beyond its own pool of one interface shaper and about 410 classes, which refuses a second shaper tree: a client limited both ways needs two (its BSS's and the uplink's). An access point has about 220 MB of RAM available, so each MB is taken from that. Unset, the firmware gets no host RAM for its shapers.
- `U6E_PCC=1` has `u6e-nss` create the NSS mirror device `mirror.0` and load `u6e-pcc` (`nss/u6e-pcc/`), our module that has ECM accelerate one client's TCP and UDP connections with an NSS mirror rule, so the NSS core copies their packets to `mirror.0` while they stay offloaded; a client capture (`u6e-capture`) sets the client. Loading it costs every access point something, whether a client is set or not: while it is registered ECM keeps every DNS (port 53) connection on the CPU, registering drops every connection from the hardware once, and it cannot be unloaded, as ECM holds it until the next boot. Unset, the module is in the image but nothing loads it, and no mirror device is created.

## Testing

`test/` checks the access points on the air, using a test client with a Wi-Fi card (set `TEST_CLIENT` in `site.conf`):

- `test/join.sh "<SSID>" [<BSSID>]` joins a network the way its kind requires, gets an address, pings the gateway and reports the association.
- `test/sniff.sh <MHz> <width> [<center MHz>] <seconds> <out.pcap>` captures radio traffic.
- `test/bip-verify.py <pcap> <BSSID> <key>` checks the beacon protection signature of every beacon in a capture.
- `U6E_AP=<ap> test/oce-retry.sh <interface> [<count>]` counts how many times a radio retries unanswered management frames (`mgmtsend.c` is its helper).

`test/ap-image.sh` needs no access point: it checks offline, with a stub `prep-rootfs.sh`, which image `ap-image.sh` picks (an image built with `BOOT=0` is the one booted next; changed inputs or a deleted image mean a new build; `FORCE=1` reuses the kept image; a failed build stops `deploy.sh` and records nothing), and, over commits to a scratch clone, that only a change to what goes into an image changes its key (a README, test, controller or controller-only dependency change does not; an agent or helper source, agent dependency or `prep-rootfs.sh` change does).

`test/helper-units.sh` needs no access point either, but root and systemd on the build host (and host builds of the helpers, `cargo build -p u6e-shaper -p u6e-capture`): it starts the `u6e-shaper@` and `u6e-capture@` units with their sandboxes exactly as `prep-rootfs.sh` writes them and checks that each one's command and last step both ran, so a sandbox systemd cannot set up (226/NAMESPACE) fails it rather than an AP. Only the binaries, the sockets' group and, where ECM is not loaded, its `/proc/sys` files are swapped for the host's; it removes everything it adds.
